# PRD 09 — 기술 아키텍처

## 1. 원칙

1. **물리 코어는 어디서나 같은 코드로 돈다.** 브라우저(플레이, 예측선), Web Worker(AI), 서버(검증), 테스트 도구(보정).
2. **계층을 분리한다.** 물리 → 규칙 → 게임 진행 → 화면. 아래 계층은 위 계층을 모른다.
3. **상태는 "초기 배치 + 샷 입력 목록"으로 표현한다.** 리플레이, 동기화, 복구가 모두 이 형식을 쓴다.
4. **서버 없이도 핵심이 돈다.** 연습, 컴퓨터 대전, 로컬 대전은 정적 호스팅만으로 동작.

## 2. 기술 스택 (제안)

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어 | TypeScript | 브라우저·서버 코드 공유 |
| 물리·규칙·AI | 순수 TypeScript, 외부 의존 없음 | 결정성, 이식성 |
| 렌더링 | Three.js | 웹 3D 표준, 가벼움 |
| UI | React (또는 Svelte) | 스코어보드, 대시보드, 설정 화면 |
| 빌드 | Vite | 빠른 개발 서버 |
| 테스트 | Vitest, Playwright | 단위 테스트, 브라우저 간 결정성 검사 |
| 서버 | Node.js + WebSocket | 물리 코어 재사용 |
| DB | PostgreSQL (초기에는 SQLite도 가능) | 계정, 경기, 통계 |
| 에셋 제작 | Blender 스크립트 → glTF | 규격 치수 기반 생성 |
| 배포 | 정적 호스팅(CDN) + 서버 1대부터 | 낮은 초기 비용 |

물리 코어의 성능이 부족하면 Rust/WebAssembly 이식을 검토한다. 단, 결정성 검증을 다시 해야 하므로 TypeScript로 충분한지 먼저 측정한다.

## 4. 계층과 데이터 흐름

```
입력(input) ──ShotInput──▶ 물리(physics) ──ShotResult──▶ 규칙(rules) ──판정──▶ 진행(game)
                               │                                              │
                               └──────────운동식──────────▶ 렌더(render)       └─▶ 스코어보드, 기록
```

- `ShotInput`: 방향, 고각, 당점, 임팩트 속도·가속도, 큐 사양.
- `ShotResult`: 이벤트 목록, 구간별 운동식, 최종 상태, 해시.
- 렌더러는 `ShotResult`의 운동식으로 임의 시각의 공 위치·자세를 계산한다. 물리를 프레임마다 다시 돌리지 않는다.

## 5. 핵심 데이터 형식

```ts
// 리플레이 = 경기의 유일한 원본
type MatchRecord = {
  coreVersion: string        // 물리 코어 버전
  discipline: '3c' | '4ball' | ...
  ruleOptions: {...}
  tableProfile: {...}        // 계수 전체를 포함 (이름 참조가 아님)
  initialBalls: BallState[]
  shots: { player: number, input: ShotInput, timeMs: number, strokeTrace?: number[] }[]
}
```

- 점수, 이닝, 통계는 모두 `MatchRecord`에서 다시 계산할 수 있다.
- 조회 성능을 위해 요약값은 DB에 따로 저장한다.

## 6. 서버

| 기능 | 내용 |
|---|---|
| 방 관리 | 생성, 참가, 관전, 설정 |
| 샷 검증 | 입력 범위 확인 → 물리 코어 실행 → 판정 확정 → 중계 |
| 매칭 | 수지 기반 대기열 |
| 저장 | 계정, MatchRecord, 요약 통계, 랭킹 |
| 인증 | 소셜 로그인, 세션 |

- 방 상태는 메모리에 두고 샷마다 저장소에 기록한다(장애 복구).
- 샷 하나의 서버 계산은 수 ms이므로 서버 1대로 다수의 방을 처리할 수 있다. 정확한 수용량은 측정 필요.

## 7. 결정성 확보 방법

- 삼각함수·지수함수는 `packages/physics/math`의 자체 구현만 사용. `Math.sin` 등 사용을 린트 규칙으로 금지.
- 연산 순서 고정 (배열 순회 순서, 이벤트 동시 발생 시 우선순위 규칙).
- 난수는 시드 기반 생성기, 시드는 MatchRecord에 포함.
- CI에서 Chrome, Firefox, Safari(WebKit), Node의 결과 해시를 비교.

## 8. 성능 설계

- 물리: 객체 할당을 줄인 숫자 배열 기반 구현. 샷당 1~5ms 목표.
- AI: Web Worker 여러 개로 후보 평가 병렬화.
- 렌더: 공은 인스턴싱 불필요(최대 16개). 병목은 그림자와 반사이므로 품질 단계로 조절.
- 로딩: 코드 분할, 압축 텍스처(KTX2), 대시보드 등은 지연 로딩.

## 9. 보안과 개인정보

- 서버는 클라이언트가 보낸 결과를 신뢰하지 않는다.
- 개인정보는 로그인 식별자와 닉네임으로 최소화.
- 스트로크 궤적은 이상 탐지와 리플레이용으로만 사용.
- 비밀값은 서버 환경 변수로만 관리.

## 10. 개발 환경

- 모노레포 (pnpm workspace).
- 물리 코어는 화면 없이 테스트 가능. 디버그용 2D 뷰어(캔버스)를 먼저 만들어 물리 개발에 사용.
- 코드 스타일: ESLint, Prettier. 커밋 전 테스트.

## 11. 미결 사항

- UI 프레임워크 확정 (React / Svelte)
- 호스팅 서비스와 예상 비용
- 로그인 제공자
- WebAssembly 이식 필요 여부 (성능 측정 후)
